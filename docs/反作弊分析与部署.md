# Dread Hunger Linux 反作弊：v1 开发版与 v2 自动踢出版

更新日期：2026-10-11。v1、v2 均只保留远距离交互、未挖掘取物、刷箭、无限子弹和传送五类检测。交互/取物阈值统一为 10 米，保留捕兽夹直接致死动物尸体的测距例外。物资数量、`Item Hoovering`、快速挥刀、快速装填、非法射击状态等类型不再触发插件公告、踢出或黑名单；相应主动检查已移除。原生游戏仍可记录这些日志或执行自己的处理。

v1 拦截异常请求并公告，不踢人；v2 对准确关联当前在线会话的事件公告、调用原生踢人接口，并按 Steam/EOS 账号登记服务器黑名单。公告只显示中文原因，英文类型和详细参数保留在诊断日志。既有黑名单和待处理请求保留，此前误封需在 GM 黑名单中心手动解除。真实 Linux 对局仍需更新插件后复测。

## 版本和处理流程

| 版本 | 文件 | 行为 |
| --- | --- | --- |
| v1 开发版 | `app/Linux 插件/[服务端]反作弊物资_Linux.js` | v2 未启用时加载，保留拦截和公告，不踢人、不写黑名单 |
| v2 自动踢出版 | `app/Linux 插件/[服务端]反作弊物资_v2_Linux.js` | 独立规则快照；`.js` 启用，改为 `.js.disabled` 停用；检测后公告、踢出并拉黑当前账号 |

v2 不依赖 v1 文件内容执行；后续在 v1 开发新检测不会直接改变 v2 的执行规则。注入器发现启用的 v2 时跳过 v1，避免两份 Hook 同时作用于游戏。

v2 将白名单内的原生直连事件和拦截事件排入队列，在 GameMode Tick 中重新核对 World、PlayerState 和控制器的引擎弱引用，再公告并调用 `AGameSession::KickPlayer`。这样不会在拾取/加物品函数尚未退出时销毁角色，也不会仅凭昵称踢人。离线、弱引用失效、同地址对象复用和旧 World 的事件忽略；同一连接成功踢出后不重复处理，重新连接的玩家按新身份处理。原生踢出失败会记录原因，后续检测事件仍可重试，不受公告冷却阻断。

公告示例：

```text
发现 宝宝巴士 随机赢对 60+ 船长 作弊
理由：无限弹药
处理：自动踢出游戏
```

v1 只显示前两行。主检测日志同样只显示中文类型；`[反作弊][证据]` 和 `[反作弊][拦截]` 日志保留英文类型、距离和详细拒绝原因。公告的“自动踢出游戏”说明开始执行操作；实际成功或失败以 `[反作弊][踢出]` / `[反作弊][踢出失败]` 为准。

日志后备事件只有昵称，不能证明当前连接身份，因此两个版本都保留公告，不按后备日志昵称踢人或拉黑。两条事件路径共用白名单：`Remote Interaction`、`Remote Loot`、`Cross Map Interacts`、`Buried Loot`、`Arrow Duplication`、`Infinite Ammo`、`Teleporting`。其余类型和未知类型直接忽略；原生 `Long Range Interacts` 的旧阈值由插件 10 米入口检查替代。

v2 从当前 PlayerState 的 `UniqueId` 读取 Steam/EOS 账号，在游戏线程核对身份后投递黑名单请求。注入器将独立请求原子保存到 `.gm_runtime/anti_cheat_blacklist/`，GM 控制台后台自动合并到现有 `gm_blacklist.json`；人工编辑与自动登记共用控制台的锁，重复账号不新增、不覆盖已有人工理由。请求保存后即使 GM 控制台暂未运行，也会在其恢复运行后处理。写入失败保留请求重试，账号 ID 无效时只踢出并记录登记失败，不按昵称拉黑。

黑名单在重启后保留，GM 黑名单中心和进服器预检均使用同一份记录。v2 每秒核对在线账号，黑名单账号重新加入也会被原生踢出；这是进入后的服务器拦截，不是握手前拒绝。管理员在 GM 黑名单中心移除记录即可解封；v1 不执行此拦截。实际保存成功以 GM 控制台的 `[反作弊][黑名单已保存]` 为准，注入器的 `[黑名单待保存]` 只表示请求已落盘。

## DH 样本的静态分析结果

样本为 `LinuxServer/DH/dh.exe`，恢复前位于 `LinuxServer/DH/DH/dh.exe`。全程只读文件，没有运行样本、加载它的 DLL 或驱动。

| 项目 | 结果 |
| --- | --- |
| 大小 | 25,464,832 字节 |
| SHA-256 | `12c722967028dbdce4a7a1912966de4e75f786be9810abcf9c0111ddaaf5f1de` |
| 外层程序 | PE32 / x86，ImageBase `0x400000` |
| 内嵌组件 | 15 个可解析的 PE 组件，其中 9 个导入 `ntoskrnl.exe`，还包含界面组件及驱动加载相关组件 |
| 游戏目标字符串 | 文件偏移 `0x1582cd2`：`DreadHunger-Win64-Shipping.exe` |
| 内存操作证据 | 外层和内嵌组件中存在 `ReadProcessMemory`、`WriteProcessMemory`；部分内嵌组件导入 `CreateRemoteThread`、`VirtualAllocEx`、`WriteProcessMemory` |
| 驱动相关证据 | 内嵌组件导入进程查找、内存读写相关内核 API；一个用户态组件导入 `NtLoadDriver`、`NtDeviceIoControlFile` |

据这些证据判断，样本具备读写客户端进程内存及注入能力，也携带驱动组件。**携带组件不等于本次运行一定加载了这些组件**；静态分析尚未还原每个开关实际写入的地址、数值和完整执行路径，不能将下面的作弊机制推测称为已确认的反编译结果。

`Neverlose.ini` 和使用说明声明的功能包括：远程摸尸/摸肉/摸鬼、范围拾取、查包、透视、快速拉弓、近战速度/距离修改、无限子弹、刷箭、出窍、飞天、强制建造、倒地交互、强制开船、去雾与夜晚高亮。这些说明仅作为样本资料，不代表每项在当前游戏版本都有效。

## 远程摸肉、射尸体刷箭漏检修复

根据本地二进制确认旧检测存在两个缺口：只监听简化 AddInventory 重载，遗漏直接调用完整重载的拾取/转移；`HitActor_Implementation` 在任何弹药校验之前就调用 `OnProjectileHitActor`，而后续原生弹药检测还会跳过死亡目标。不能靠提高数量敏感度覆盖这些路径。

- TransferInventory 同时检查来源和目标，PickUp 检查拾取对象。超距请求在原函数执行前拒绝，日志出现 `[反作弊][拦截] ... Remote Loot`，下一次 Tick 公告“远程摸物资/摸尸”。距离使用服务端玩家位置到对象包围盒的最近距离，检测阈值按用户要求统一为 **1000 cm，即 10 米**；等于阈值放行，超过时拦截。自己的背包使用持有者位置；正常近距离取物放行。
- 直接 Interact 检查目标组件的碰撞最近点，无简单碰撞时使用组件世界位置。避免船体整体巨大包围盒造成远处按钮仍被视为近距离。与取物共用 `InteractionRangeCm = 1000`，不再随游戏 `InteractRange` 字段变化；原生 `Long Range Interacts` 使用 `InteractRange * 3`（默认约 4.8 米），其直连/后备事件不再作为插件处罚依据，统一按插件 10 米检查。仅调整反作弊阈值，原版交互可达性仍由游戏控制。
- 冰墙/梯子交互单独按服务端 `ADH_ClimbableActor` 及其蓝图子类的整体边界最近点测距。大型攀爬组件没有简单碰撞时，其原点可能远离贴墙玩家，不能直接当作交互点。仍使用 10 米阈值，原版决定是否能开始/结束攀爬；不凭玩家“正在攀爬”状态放行其他交互，也不为攀爬登记物品拾取许可。箱子和船上按钮继续走组件检测。
- 捕兽夹击杀后尸体滑动：实服反馈旧修复仍误报 6.50 米。重新核对二进制后确认，`SetDeathState` 在 `NM_DedicatedServer` 跳过尸体布娃娃物理，`ConvertToCarcass` 也不在专服创建 CarcassMesh；GetComponentBounds 只读取缓存，无法取得客户端独立滑动后的尸体位置。按用户选择，**仅对本插件加载后观察到捕兽夹直接致死的动物尸体跳过距离检查**，覆盖交互、双向物资转移和拾取；不修改游戏的可交互性、埋雪判定或其他反作弊规则。这会减少该类尸体的远程作弊检测能力。捕兽夹调用时存活、调用结束后死亡才登记，原版致死路径返回 false，且死亡目标不会执行 Ensnare。活体、玩家尸体、未观察到夹子致死的动物（包括先被夹住再被武器击杀）、热加载前的既有尸体及其他物资继续使用 10 米限制；另一端的远处容器同样检查。登记使用弱对象身份，过期对象和换 World 不继承例外。已补充服务端缓存停在旧位置的 6.50 米回归，实际狼/熊场景仍需更新插件后实服复测。启动日志应包含“捕兽夹致死动物尸体跳过测距”，成功观察到夹子致死时输出 `[反作弊][捕兽夹尸体] 已登记距离检查例外`。
- v3.2：截图中 F 丢弃后 E 拾取被第二次测距判为 2.59 米。交互开始检查碰撞最近点，旧拾取入口又检查 Actor 包围盒；本地原生拾取交互时间为 0.5 秒，期间有物理运动与抓取步骤。通过 2.5 米起始检查且原版接受的交互，只在 `OnInteractComplete` 执行期间授权同一玩家、控制器、目标组件、物品 Actor 和槽位的一次拾取。取消/拒绝、换目标、无起始记录、重放完成或完成范围外的直接拾取仍走距离检查；没有按自己的掉落物作整体豁免，也没有扩大距离。该调整经模拟对象回归验证，真实误报原因与修复效果仍需实服复测。
- 弓的类型依据服务端 `EInventoryType::CCT_BOW = 36`。在 Ranged Use 执行期间，只有确认服务器 UsesRemaining 减少 1，且进入发射 Flash 时，才记入一支箭。每次 HitActor 只能消费一个记录，覆盖尸体与活体；额外命中在回收箭的蓝图事件前拒绝并公告“刷箭/伪造弓箭命中”。最后一支合法箭命中时 UsesRemaining 已为 0，仍能凭对应发射记录放行。
- 发射记录保留 30 秒；热加载后的前 30 秒允许未被本插件观察到的已有飞行箭。复测刷箭应在新插件启动至少 30 秒后进行。公告同玩家同类型冷却 60 秒，日志拦截提示冷却 10 秒。
- 服务端主动设置的 `bInfiniteItems` 或武器 `MaxUses <= 0` 沿用服务器设定；客户端无限弹药开关不会改变这些服务端字段。v3 将相同的发射核对扩展到手枪（26）和步枪（27），额外枪械命中使用 Infinite Ammo 理由。
- 完整 AddInventory 入口只 Hook 一次，避免简化重载嵌套造成重复计数；CreatedBy 为空时按背包所属角色归属，保留 GM/赢牌可信物资豁免。

发射与命中计数限制额外回收箭，尚未按投射物 UID 精确对应每次命中，也未验证命中的空间真实性。自定义弓、超长飞行箭、插件生成箭和真实网络延迟仍需实服验收。此次没有连接用户服务器，也没有执行外挂样本。

## 保留的弹药检查

- 不再监听近战 Use、骨刀瞄准和 Reload 开始入口，不再按挥刀冷却、装填定时器或开始记录拒绝操作。
- 保留 RangedReload 和 CompleteReload 核对：填满弹匣前，确认当前原生装填调用使对应背包弹药实际减少 1；无扣弹或绕过该入口直接补弹，报告 `Infinite Ammo`。
- 最后一颗备用弹药销毁后，权威 StackCount 变为 0，仍符合扣弹校验；服务器免扣弹/无限物品配置和热加载 30 秒宽限保留。正常扣弹的连续装填不会因速度被插件处罚。

这些检查覆盖当前已核实的入口，尚未覆盖所有直接改写弹药状态的路径。

## v3.3 雪下取物和图腾建造

雪下物资以服务端雪堆的 `BuriedActor`（`0x298`）和 `bDugUp`（`0x2A0`）关联。未挖完时，在直接交互、物资转移和拾取进入原函数之前拒绝，中文公告为“未挖掘取物”。不依赖物资所在高度、固定挖掘次数或血量；部分挖掘、甚至血量为零但挖完状态尚未更新，都不能放行。挖完后沿用原来的交互流程，包括 v3.2 的正常拾取完成授权。

每个 World 首次取物时只枚举一次 DigSite，覆盖插件热加载前已有雪堆；新生成/流式加载通过 `OnRep_BuriedActor` 登记。索引使用引擎弱引用，同时复核雪堆是否仍指向同一物资，避免销毁后指针复用误判；更换 World 时重建。原生枚举数组由引擎释放，不在每次拾取或每帧重新扫描地图。

非法图腾建造检测已移除：删除放置入口 Hook、服务端额外地面/坡度/碰撞/配方校验和对应原生调用绑定。图腾放置、材料投入和完成建造交回游戏原版。插件收到 `Invalid Totem Placement` 原生事件或旧日志时直接忽略，不公告、不踢人、不生成黑名单请求；已有账号黑名单保留，管理员可在 GM 黑名单中心处理此前误判记录。

近战请求全部交给原版；插件不再按近战命中、冷却或相关原生事件处罚。

## 历史记录：v3.3.1 GM 发物品误报修复

以下描述旧版数量检测的修复。当前反作弊消费端已随数量检测移除，GM/奖励生产端保持原样。

本地真实 Frida 17.16.1 文件测试确认：`File.writeAllText` 用较短 JSON 覆盖已有文件时，会留下旧尾部。反作弊消费可信发放记录后写入 `{"grants":[]}`，旧发放数据仍残留在其后，下一次 JSON 解析失败；GM 原来的登记函数又在解析错误时直接退出，后续 GM 发物品被当作未可信增加，达到数量阈值就出现“刷物资”。这是已复现的代码缺陷，尚未读取用户本次实服运行记录。

GM、反作弊消费端、赢牌奖励三个共享文件写入点统一改为 `new File(path, 'w')`，写完关闭，截断旧尾部。GM 遇到旧损坏 JSON 时重新建立可信记录，无须手工删除文件；每次成功或背包未收下物品的调用都消费自己的单次凭据，保留其他玩家/物品的未消费凭据。GM 若无法写入可信记录，返回明确失败，不继续发物品。

这项修复不豁免 GM 接收者随后进行的拾取、射击或刷取，也不提高数量阈值。
